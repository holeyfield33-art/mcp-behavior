# Behavioral assessment specification 1.0.0

## 1. Scope and trust model

The harness launches a configured stdio MCP server, invokes one explicitly selected synchronous tool, supplies known fixtures, and independently checks its outputs and observable effects. It has its own repository, package, tests and specification. Other software can be a test subject; no implementation dependency on it is permitted.

The trusted computing base consists of the reviewer-owned profile, harness/client/oracle, operating system, and evidence writer. Tool descriptions, annotations, tool results, logs, tool-provided schemas and version strings are untrusted observations. Schemas are not fetched, executed, or accepted as scoring policy. No result is evaluated by an LLM.

An independent oracle is mandatory but insufficient on its own: a target with access to the oracle or reports can tamper with evidence. Native mode is available for development and records required containment UNKNOWN. Resource caps do not establish isolation. A future isolated runner must hide oracle/evidence storage, deny undeclared host/network access, enforce descendant limits and validate those controls from outside the target.

## 2. Profiles and applicability

The v1 profile is a read-only repository inventory contract, with `.py`, `.js` and/or `.txt` as explicitly supported regular-file suffixes. Suffix comparison is case-sensitive. Hidden files are included. Other regular files must be explicitly excluded with a reason. Directories are traversal structure; symlink directories are unsafe entries. All symlinks and non-regular files require a reasoned refusal. The profile does not infer these capabilities from advertising.

The reviewer provides:

- A named, versioned profile and digest.
- A named tool, one path argument, constant additional arguments and supported suffixes.
- A relative-path policy: `reject`, or `workspace` using the advertised client root. Server CWD is a separate decoy.
- Pointers to processed, excluded and failed file records, their path/reason/hash fields, optional counts and an optional boolean completion flag.
- A caller-visible wire-byte budget and time/resource budgets.
- A narrowly enumerated set of timestamp leaves allowed to vary.

An absent mapping is UNKNOWN. A configured field missing from the result, a wrong type, overlapping/duplicate paths, false counters or inconsistent representations is a response-contract FAIL. This distinction prevents an unsuitable adapter from silently supplying proof.

Mappings are declarative. There is no plugin execution, regex scoring language, `eval`, shell interpolation, server-provided answer key or automatic grading-rule discovery.

A scanner may expose processed files without content digests or finding-level ground truth. That can establish some coverage behavior. It cannot establish semantic finding correctness; the content check is UNKNOWN. Correctness for more tool types requires a new independently reviewed oracle.

## 3. Client contract

The client offers a dated stateful protocol revision and validates the negotiated revision against its supported set. It sends `notifications/initialized`, discovers tools with bounded pagination, and invokes the explicitly configured tool. It answers ping and roots/list. Roots are not assumed to provide an OS security boundary; root restrictions are this profile's behavioral contract.

Tool annotations are never used as evidence of read-only behavior. Server instructions are inert text. The client never follows returned URLs/resources, downloads schemas, executes returned commands, installs dependencies, or provides sampling/elicitation/model capabilities.

Newline-delimited UTF-8 JSON-RPC is read in bounded chunks. Frames, session bytes, stderr bytes and message counts are bounded before JSON decoding/queue growth. Invalid UTF-8, JSON duplicates/nonfinite literals, bad envelopes, wrong response IDs, cursor loops, missing tools, disconnects, and unsupported features have explicit outcomes.

No claim of full MCP conformance is made. Unsupported revisions, media/resource outputs, task-only tools or requested unsupported capabilities are UNKNOWN. Proven malformed traffic or violated agreed limits is FAIL. A server's stderr logging alone is not failure.

## 4. Fixture and observation contract

Each run gets fresh random names/tokens so hard-coded answers for public fixtures do not suffice. Expected file bytes and manifests are generated by the harness; no answer-key file is placed in the server workspace. Independent before/after snapshots use lstat, do not recurse through symlinks, do not open special files, and bound reads/entries. Mode-000 input is opened by the oracle before chmod so its post-run bytes can still be checked with a non-inherited descriptor.

The directory layout contains three independently known trees: authorized workspace, decoy server CWD and readable outside canary directory. Disposable HOME/TMPDIR are separate from the watched tree. The outside directory is intentionally readable: a mount denial must not be mistaken for the server enforcing its declared root.

An independent permission probe runs our own code under the same execution identity/capability setup, records UID/GID/capabilities/no-new-privileges, and verifies outside/CWD canary readability. If it can read a supposed unreadable file, or cannot read a canary that must be accessible, that scenario has required UNKNOWN evidence. A server reporting a permission failure is not sufficient proof that permissions actually denied access.

The baseline covers mixed languages, empty files, no trailing newline, nested spaces, Unicode and hidden paths. The stress fixture has 709 regular files, including a file with 512 ordinary source-level sink functions. Size is measured in wire bytes, never guessed from token counts.

All scenarios use fresh sessions except the deliberate same-session repeat and repaired request. The repeatability comparison also uses a fresh session over the identical unchanged fixture. No automatic retry can erase an earlier failure.

## 5. Required checks

| Check | PASS evidence | FAIL evidence | UNKNOWN evidence |
|---|---|---|---|
| Error reason | Invalid input is identified and a concrete cause matches the profile contract | Success on invalid input, generic error, echoed filename without a cause | Request could not be exercised by this client |
| Output budget | Stress result fits, or explicit size refusal explains how to narrow/reduce/page | Frame/result/session byte ceiling is exceeded, including client cutoff | An unrelated error prevents the size scenario |
| Coverage | Every planted entry reconciles to one processed/excluded/failed record with applicable reasons | Missing supported work, unaccounted inputs, duplicates, invented inputs or false counts | Required evidence selectors are unavailable |
| Content | Processed inventory hashes equal independent bytes | Wrong hashes or failed/omitted valid required files under a hash oracle | No independently meaningful semantic/content oracle |
| Completion | Flag matches observed processed/failed required work | Complete with omitted/failed required work; unexplained partial baseline | Flag is not exposed/mapped |
| Root/entry policy | Absolute authorized root works; relative policy and explicit boundary refusals hold | CWD-dependent relative behavior, outside-root success/disclosure, unsafe processed entries | Precondition/observation cannot be established |
| Repeatability | Three normalized results agree across same/fresh sessions | Difference remains beyond approved timestamps/set ordering, or a repeated valid request errors | Three usable results were not collected |
| Read-only | Watched bytes/entries/permissions/modification metadata stay fixed | Any observable watched change | Snapshot unreadable/incomplete or observer failure |
| Scripted recovery | Reasoned bad-path error followed by a correct repaired request in that session | Unusable error or incorrect repaired result | Repair evidence lacks a content oracle or could not be collected |
| Execution containment | Reserved for independently validated isolation backend | Observed escape/tampering, when observable | Always in v1 native mode |

Refusing an unsafe whole request is allowed if it explains why; returning a quiet partial success is not. Refusing an oversized result must not be counted as correctness of the requested large scan. Coverage/correctness and the size budget remain separate checks.

Error-reason checks use deterministic literal contracts, not a claim that arbitrary prose is helpful to every agent. Real-model recovery is N/A/out of scope and cannot improve the fixture grade.

## 6. Completion and determinism details

`complete` is a boolean. Declared unsupported regular files may be excluded. Failed required supported work, or omitted expected supported files, makes a success completion claim false. Unsafe-entry refusals must remain visible. Error results cannot simultaneously claim successful completion in their mapped structured completion field.

Canonical JSON normalizes object-key ordering. Processed/excluded/failed evidence arrays are sets sorted by their mapped path for comparisons. All other array order is preserved. A profile may ignore only explicit ISO timestamp leaves with timezone, optionally through at most two array wildcards; e.g. `/plans/*/generated_at`. It cannot ignore the response root, coverage, findings, arbitrary metadata or digest fields. Every normalization rule is reported and hashed into the profile.

No live-data tolerance, statistical repeatability or numerical tolerance is inferred in this profile.

## 7. Outcomes and evidence provenance

Required demonstrated FAIL dominates UNKNOWN. Required UNKNOWN or N/A prevents PASS. An empty set of required checks is INCOMPLETE. Optional excluded checks cannot supply proof. There is no weighted score and no baseline/allowlist that erases a known failure.

Readiness and security are computed independently. Overall PASS requires all required checks across both lanes. A failure remains a failure even if the harness prevented its consequences. Unsupported features and harness defects are distinguished from observed server faults.

Reports bind a run ID, UTC time, harness version, profile/version/hash, config hash, reviewer version label, separately labeled server-reported identity, explicit executable/artifact hashes, actual negotiated protocol, tool-definition fingerprints, all budgets, fixture manifests, response wire hashes/lengths, snapshot hashes, changed entries, unknowns and limitations. Server version strings are not an artifact attestation. This prototype does not attest the full installed dependency closure.

Raw unlimited output and stderr are not retained. Oversized output records a bounded observed byte count/cutoff rather than a fabricated complete response hash. Human reports contain no active server-supplied HTML; JSON uses escaped text. Report files are written by the controller after session cleanup, outside fixture trees.

The CLI writes an INCOMPLETE/RUNNING marker before launching and commits FINISHED JSON last. Exit 0 is PASS, 1 is FAIL, 2 is INCOMPLETE. Consumers require matching run ID, FINISHED state and successful exit. If the destination cannot be written, no new report is claimed.

## 8. Implementation gate

This spec closes policy ambiguity by either implementing a check or explicitly withholding a verdict. It does not assert that every engineering risk is solved. Host isolation, syscall read/write observation, cgroup-wide resource/descendant enforcement, race testing, full dependency attestation, concurrent/multi-tenant execution and real-model behavior are open gates. Native assessments must not be published as broad security certifications.

## 9. Pre-release isolation implementation status — 2026-10-30

The behavioral profile and specification version remain 1.0.0. Development checkpoint 3 adds trusted infrastructure observations without changing fixture scoring or claiming a 0.2.0 release.

`--isolation native` (or `--native`) runs reviewed MCP subjects with required containment UNKNOWN. `--isolation namespace` runs fixed controller-owned preflight helpers only and refuses the configured subject. `--cgroup-parent` optionally supplies an existing explicitly delegated canonical cgroup-v2 path for a fixed detached-helper self-test; it is invalid with native mode. Requested policy and its digest are distinct from observed enforcement.

Infrastructure probes require their own valid fixtures, typed complete evidence, run nonces, bounds and positive/negative controls. A probe timeout, output cutoff, malformed evidence, missing prerequisite or observer/cleanup fault is failed infrastructure evidence, not a demonstrated MCP server defect. All synthetic probe successes still leave required run-level containment UNKNOWN and zero subject cases at this checkpoint.

The TCP observer checks only controlled IPv4/IPv6 loopback endpoints and requires externally received host positive controls. Traffic received from the isolated helper disproves candidate denial regardless of helper text. Absence of traffic alone cannot supply a pass. The cgroup self-test verifies genuine filesystem type, existing delegation, new-leaf limit readback, membership before release, a detached trusted child and recursive kill/empty/removal. CPU bandwidth is not a lifetime CPU budget; cumulative usage is separately sampled. A full resource-stress test and actual subject integration remain required.

A skipped host integration test is missing acceptance evidence. A fake control-file directory, feature-file presence, launcher flag or unverified helper success cannot satisfy execution_containment. Other protocols/routes, full forbidden-read and transient-write/race coverage, controller/oracle protection and dependency closure remain open under section 8.
